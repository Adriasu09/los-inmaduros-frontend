## Prerequisito backend del formulario de edición (VERIFICADO 23-jul contra el código)

Reviso `reference/los-inmaduros-fastapi` (rama `main`) para cerrar la incógnita que CLAUDE.md §1 marca como bloqueante:

- **Edición de meeting points: NO disponible.** El schema del PATCH (`RouteCallUpdateIn`) **no tiene campo `meeting_points`**, y `update_route_call` solo aplica los campos enviados de ese schema. La tabla `meeting_points` **sigue sin columna `updatedAt`** (el modelo solo tiene `createdAt`; el propio `MeetingPointOut` comenta "the table has no updatedAt"). No hay migración Alembic que lo añada.
  → **El formulario de edición NO debe exponer edición de puntos de encuentro.** Alcance del edit = `title`, `description`, `image`, `dateRoute`, `paces`.
- **Reglas del PATCH confirmadas** (para el gating de la UI y el schema del edit):
  - **Organizer only** (403 si no); permiso **antes** que estado (D18: `404 → 403 → 400`).
  - Editable **solo en `SCHEDULED`**: COMPLETED, CANCELLED y ONGOING → 400 (coincide con "Editar visible solo si SCHEDULED").
  - **Update parcial**: solo se aplican los campos enviados → enviar solo los cambiados (como pide el gherkin).
  - Campos: `title` (opcional, no-null); `description` (opcional, **null la borra** — funcionalidad real); `image` (opcional, URL http(s), no-null); `dateRoute` (opcional, futura, no-null); `paces` (opcional, 1–7, no-null).
- **Discrepancia menor de `title`:** el contrato/frontend usan 3–100, pero el backend implementa min 1 / **max 200**. El frontend es más estricto (seguro). Reutilizar en el edit la misma regla que en crear (3–100). *(Que el backend diverja de su propio contrato es cosa suya, no del frontend.)*
